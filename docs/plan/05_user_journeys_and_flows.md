## 1. State Machine Specifications

In strict adherence to **Non-Negotiable Working Rule 5 (PROPER FLOW)**, all platform lifecycles are governed by deterministic, formal finite-state machines.

```
STATE MACHINE OVERVIEW

1. SUBMISSION:
[DRAFT] --> [CHECKING] --> [PENDING_REVIEW] ----> [APPROVED]
                                |         ^
                                v         |
                            [SENT_BACK] --+ (Resubmit v2)

2. CHECK RUN & JOB:
[QUEUED] --> [RUNNING] ----> [COMPLETED] (All stages clean)
                 |---------> [PARTIAL]   (AI fails; deterministic retained)
                 +---------> [FAILED]    (Fatal parse/validation crash)

3. FINDING VERIFICATION:
[CANDIDATE] ----> [VERIFIED]   (Receipts A & B confirmed -> Displayed)
             +--> [UNVERIFIED] (Receipt mismatch -> Flagged/suppressed)
             +--> [DROPPED]    (Quote not found -> Dropped from confirmed view)

4. RULE LIFECYCLE:
[DRAFT] --------> [APPROVED] (Mandatory human approver ID) --> [ACTIVE] (In policy v1.0)
       +--------> [REJECTED]
```

### 1.1 State Machine SM-01: Submission Lifecycle (`submission.status`)
- **States:**
  - `DRAFT`: Initial draft created, content uploaded; no check has been executed.
  - `CHECKING`: Background verification job is actively executing.
  - `CLEAN`: Check completed with zero policy violations detected.
  - `PENDING_REVIEW`: Check completed with one or more findings awaiting human adjudication.
  - `SENT_BACK`: Reviewer or approver rejected the draft with remediation notes.
  - `APPROVED`: Formal sign-off granted by authorized approver; ready for external publication.
  - `ARCHIVED`: Obsolete or cancelled submission retained for audit history.
- **Allowed Transitions:**
  - `DRAFT` $\to$ `CHECKING` (on check run triggered)
  - `CHECKING` $\to$ `CLEAN` (check run completes with 0 findings)
  - `CHECKING` $\to$ `PENDING_REVIEW` (check run completes with $\ge 1$ findings)
  - `CHECKING` $\to$ `DRAFT` (check run fatal failure; returns with error state)
  - `CLEAN` $\to$ `APPROVED` (one-click fast-track approval)
  - `CLEAN` $\to$ `CHECKING` (new resubmission version uploaded)
  - `PENDING_REVIEW` $\to$ `SENT_BACK` (reviewer rejects with notes)
  - `PENDING_REVIEW` $\to$ `APPROVED` (approver signs off with all critical findings resolved)
  - `PENDING_REVIEW` $\to$ `CHECKING` (creator uploads revised version `v2`)
  - `SENT_BACK` $\to$ `CHECKING` (creator resubmits new version `v2`)
  - `APPROVED` $\to$ `ARCHIVED` (administrative action)

---

### 1.2 State Machine SM-02: Check Run & Background Job (`job.status`, `check_run.status`)
- **States:**
  - `QUEUED`: Check task registered in database job table; awaiting background execution.
  - `RUNNING`: Worker thread executing parsing, deterministic checks, or LLM analysis.
  - `COMPLETED`: Pipeline completed all stages successfully with verified outputs.
  - `PARTIAL`: Deterministic checks succeeded, but external LLM timed out or failed schema validation after 1 retry; deterministic findings are preserved.
  - `FAILED`: Unrecoverable exception during initial parsing or normalisation.
- **Allowed Transitions:**
  - `QUEUED` $\to$ `RUNNING`
  - `RUNNING` $\to$ `COMPLETED`
  - `RUNNING` $\to$ `PARTIAL`
  - `RUNNING` $\to$ `FAILED`

---

### 1.3 State Machine SM-03: Finding Verification Status (`finding.verification_status`)
- **States:**
  - `CANDIDATE`: Finding generated by deterministic regex or LLM parser; unverified.
  - `VERIFIED`: Programmatic verifier confirms flagged text in submission AND source quote in policy document.
  - `UNVERIFIED`: Verifier unable to confirm source citation with confidence $\ge 0.85$.
  - `DROPPED`: Source quote or submission span cannot be located; discarded from confirmed reviewer UI.
- **Allowed Transitions:**
  - `CANDIDATE` $\to$ `VERIFIED`
  - `CANDIDATE` $\to$ `UNVERIFIED`
  - `CANDIDATE` $\to$ `DROPPED`

---

### 1.4 State Machine SM-04: Finding Review Adjudication (`finding.review_status`)
- **States:**
  - `OPEN`: Initial confirmed finding awaiting human action.
  - `ACCEPTED`: Creator or reviewer accepted the finding and agreed to modify text.
  - `REJECTED`: Reviewer dismissed finding as non-applicable.
  - `EDITED`: Reviewer or creator modified text directly in response to finding.
  - `OVERRIDDEN`: Reviewer authorized a formal policy exception; requires `reason_code`.
  - `DISPUTED`: Creator formally contested the finding; awaiting reviewer review.
- **Allowed Transitions:**
  - `OPEN` $\to$ `ACCEPTED` | `REJECTED` | `EDITED` | `OVERRIDDEN` | `DISPUTED`
  - `DISPUTED` $\to$ `ACCEPTED` | `REJECTED` | `OVERRIDDEN` (resolved by reviewer)

---

### 1.5 State Machine SM-05: Brand Rule Lifecycle (`rule.status`)
- **States:**
  - `DRAFT`: Candidate rule proposed by document compiler or human edit; non-binding.
  - `APPROVED`: Formally confirmed by authenticated brand manager (`approved_by` set).
  - `REJECTED`: Candidate rule dismissed during compilation review.
  - `ARCHIVED`: Rule retired in subsequent policy versions.
- **Allowed Transitions:**
  - `DRAFT` $\to$ `APPROVED` | `REJECTED`
  - `APPROVED` $\to$ `ARCHIVED`

---

### 1.6 State Machine SM-06: Policy Version Lifecycle (`policy_version.status`)
- **States:**
  - `DRAFT`: Working version container being assembled with approved rules.
  - `ACTIVE`: The current, binding policy version for the workspace (`is_active = TRUE`).
  - `SUPERSEDED`: Historical immutable policy version replaced by a newer release.
- **Allowed Transitions:**
  - `DRAFT` $\to$ `ACTIVE` (on publication)
  - `ACTIVE` $\to$ `SUPERSEDED` (when next version is published)

---

### 1.7 State Machine SM-07: Rule Change Proposal (`rule_change_proposal.status`)
- **States:**
  - `DRAFT`: Proposed rule diff synthesized from accumulated override patterns.
  - `BACKTESTING`: Simulation engine actively replaying historical submissions.
  - `BACKTESTED`: Simulation run complete; empirical impact report available.
  - `ADOPTED`: Brand manager approved proposal; compiled into new policy version.
  - `REJECTED`: Proposal dismissed by brand manager.
- **Allowed Transitions:**
  - `DRAFT` $\to$ `BACKTESTING` $\to$ `BACKTESTED` $\to$ `ADOPTED` | `REJECTED`
